# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

"Release Tycoon" (formerly "Release Manager"): a small browser game for mobile, in Swedish, with the stress of air traffic control. Changes (bug fixes, security fixes, database changes, API changes) fall down an inbox, and the player drags or taps them into one of three releases before they hit the bottom. The rules aim to be realistic: nothing disappears, deadlines belong to issues and not to releases, API halves can't be split, and database migrations ship in version order. Plain HTML/CSS/JS with no build step and no dependencies. Regression tests live in `tests.html`.

## Publishing

The game is live on GitHub Pages at https://gustafbratt.github.io/Release-game/, built from the `gh-pages` branch. The user wants every change to go live at once: after each finished change, commit (Swedish message) and push to both branches with `git push origin main main:gh-pages`, without asking first. Bump the `?v=` number on `style.css` and `game.js` in `index.html` with every push, so phones don't keep a cached old file. `scripts/pre-commit` does this automatically, but only if the user has installed it (`cp scripts/pre-commit .git/hooks/`); installing hooks yourself is blocked, so otherwise bump it by hand.

## Running

```
python -m http.server 8765 --bind 127.0.0.1
```

Then open http://127.0.0.1:8765/. Opening `index.html` as a file works in a normal browser, but Claude's built-in browser can't drive `file://` pages. Test at phone width (375×812).

To test rules without playing, drive the game from the page console: `start()`, `spawnCard(type, {module})`, `tryPlace(cardId, G.releases[i])`, `startDeploy(r)` and `update(dt)` are globals, and calling `update(0.05)` in a loop fast-forwards the game. After each `start()`, add every key to `G.seenTips`, or info cards will pause the simulation. Remove `localStorage['rm-hi']` afterwards.

## Tests

Open http://127.0.0.1:8765/tests.html: it loads the game in an iframe and runs every scenario inside it (via `eval`, so tests see the game's functions and `G`), then lists the results; `window.testResult` holds `{ pass, fail }`. Run it after every change, before pushing, and add a test for every bug fixed or rule added. `fresh(score)` starts a game with info cards marked seen and random spawns off; `run(seconds)` fast-forwards; `botGame(rate, seconds)` plays a whole game. The last row is a balance report (how long bots survive), information rather than a pass/fail check. It saves and restores `localStorage['rm-hi']`.

## Structure

- `index.html`: HUD, inbox (`#inbox`), release lanes (`#releases`), and the overlays. The start overlay holds every instruction text as `<section class="page">` blocks, used three ways by `openIntro` in `game.js`: the pages marked `data-start` (two) before the first game; a single page as an **info card** (`introMode = 'tip'`) the first time its mechanic comes up in play; and, from the pause screen, the start pages plus every card seen so far. Info cards are triggered by `tip(key)` calls next to the mechanic (first conflict, first db spawn and so on). They pause the game (`tipOpen` keeps `setPaused(false)` from resuming) and queue up if several fire at once. Every game shows each card again the first time its mechanic comes up (`G.seenTips`, reset per game): the user wants the cards every time, so don't make them persist. Rule numbers in the texts are written by hand, so update them when rules change.
- `style.css`: everything visual. Theme colors are variables on `:root`. `--cw`/`--ch` (card size) are set from JS.
- `game.js`: all logic, in one file and in this order: rule constants and content (`TYPES`, `MODULES`, titles, PI constants), helpers, sound (lo-fi and chip instruments, `sfx`, both music sequencers), DOM refs and `measure`, state (`newGame`), unlocks and pace, spawning, rules, rendering, the loop, PI planning, input, screens and info cards. Functions and `G` are globals (top-level `let`/`const`/`function` in a classic script), which is what the console and `tests.html` rely on.
- `tests.html`: the regression tests (see above). `scripts/pre-commit`: the optional version-bumping hook.

**State vs DOM.** `G` holds the game. A card is `where: 'inbox'` (it has its own `el`, positioned by `progress` 0→1 each frame, and slips into a release at 1) or `where: 'release'` (no `el` of its own, drawn as a slot by `renderLane`). Lanes are re-rendered with innerHTML on every structural change. Per-frame updates (timers, bars) go through refs cached on the lane element (`_time`, `_ship`, `_dues`, `_label`). Input is delegated at `document` level with pointer events, so re-rendering a lane mid-tap is safe. A drag moves a clone (`.ghost`), not the card.

**Lanes are always in version order.** `G.releases` is an array where index = `r.lane`. When a release ships, `rotateReleases` removes it, the ones to its right slide left (`r.lane` is renumbered and every lane re-rendered), and a new release enters on the right. Releases have no date or timer: they ship only when the player presses Släpp, or when one reaches `FORCE_SLOTS` (the boss deploys it). Only the leftmost release (`lane 0`) can ship, so versions reach prod in order. The other lanes' buttons say "Efter v…". While lane 0 deploys, lane 1 can be queued (`canQueue`, `r.queued`, a chess-style pre-move): pressing its button again cancels, and `rotateReleases` starts it as soon as it becomes lane 0, unless a conflict is unresolved by then. Anything that refers to a release over time uses `r.id`, never the lane index.

Integers shown to the player go through `fmt()` (Swedish thousands separators, `12 345`).

**There is no health meter.** The game runs until the player makes one of three serious mistakes, each calling `gameOver(title, why)`, which shows the reason: releasing migrations out of order, releasing an incomplete API change (both checked in `finishDeploy`), or missing a deadline (`missDeadline`). Släpp is deliberately *not* disabled for the first two: the lane warns instead (a red "⛔ …" label from `blockingMigrations`/`incompleteApi`, and a red `.ship.danger` button), so the mistake stays the player's. Smaller mistakes only cost time and therefore points.

**Rules** (enforced in `canPlace`, `tryPlace`, `placeInto` and `finishDeploy`):
- **Speed is the goal.** Points per change are `TYPES[type].points × speedFactor(c)`, where the factor falls from 2× (instant) to 0.2× by lead time since `c.born` (kept through rollbacks). The cost of releasing is the **pipeline**: only one release deploys at a time (`pipelineBusy()`), for `DEPLOY_TIME` seconds, so the player has to batch.
- **Changes in the same service in one release are merged** (the user's rule): `movers(c)` is every card in `c`'s release with the same `module`, and they move together. Nothing else moves along: cards of different services move independently, and so do the cards of an API change (the user wants to move those one by one). `canPlace` checks room and migration order for the whole set, and `tryPlace` moves it. A git conflict follows its cards (progress and `spont` flag carried over, no new alarm via `placeInto`'s `quiet`), so moving can neither dodge nor restart one. During PI planning every card moves on its own. Selecting a card in a release highlights everything that would move with it.
- 4 planned slots per release, and a db change takes 2. In player-facing text everything is an "ändring" (not "story" or "plats"): "En release kan ha max 4 ändringar", and a db change counts as 2. The PI cards are `story` in code but "ny ändring" to the player. A lane's header shows the earliest deadline (`minDue`) among its cards. Cards have no time bar: their height on the radar is the timer. Cards never overlap: each of the three columns is a queue (`cardGap`), so a faster card stops behind a slower one, and a new card enters the column with the most room (`enterInbox`), waiting just above the radar (negative `progress`) if every column is full at the top. The radar label counts the ones mostly out of sight ("… till på väg in").
- **Nothing disappears.** A card that reaches the bottom calls `slip`: it goes into the leftmost open release (or its API partner's release) as `unplanned`, ignoring capacity and the other rules. When it ships it gives half points. An overfull release shows "📦 Överfull", and `renderLane` squeezes its slots (`--sh`) so the lane keeps its height. A slipped card can cause a conflict, or make the leftmost release hold an out-of-order migration or a partial API change.
- Two cards in the same module in one release create a conflict that takes `CONFLICT_TAPS` taps to resolve. A spontaneous conflict ("main moved on") needs only one card in that module (`spont`). Släpp is disabled while a conflict is unresolved. If the release ships anyway (the boss), it's a rollback: the cards go back to the inbox, keeping their flags and `born`, so the lost time costs points.
- **API changes are never split.** An API change is a group of 2–4 cards in distinct services (`G.pairs`, one server plus clients, sharing a letter shown as e.g. "A×3"). Groups are 2 cards until `apiBig`, then 2–3, and 2–4 from `api4` (`groupSize`). Clients spawn 1–3 s apart via `G.scheduled` (each entry carries `pid`). The cards are placed and moved one by one, and a card that reaches the bottom slips into the release where the rest of its change already is. Releasing before all members are in the release (including ones still in `G.scheduled`) is game over.
- **Deadlines are on issues** (`dueLeft`). Security fixes always get `SEC_DUE`, and once `deadline` is unlocked some bug and db cards get a customer deadline. The clock runs wherever the card is, except while its release deploys. A missed deadline is game over. A customer deadline met gives `DUE_BONUS`.
- **Migrations ship in version order.** (Don't name a specific migration tool in the game: keep it generic.) Every db card gets an increasing `dbv` (V41, V42 …). `canPlace` keeps planned migrations in version order left to right across lanes. Once `dbOrder` is unlocked, `nextMigration` sometimes skips a number and holds it back in `G.pendingDbv`, so V62 can appear 2–5 s before V61. The top bar shows the schema version in prod (`G.dbProd`, starting at V40, raised when migrations ship), but only from the first migration shipped (`G.dbShown`): the user doesn't want it before then. `missingMigrations(r)` lists older migrations neither in prod nor in `r`, including held-back ones that haven't appeared yet. Releasing while it's non-empty is game over. `blockingMigrations` (the missing ones not in an earlier lane) drives the red "⛔ V… saknas" lane label.
- **New kinds of changes are unlocked by points** (the user's choice: stars, not time). `UNLOCK` holds star thresholds, checked with `unlocked(key)` (`G.score >= UNLOCK[key]`; the score never drops, so unlocks stick): db 1 500, security 3 000, API pairs 4 500, out-of-order migrations 6 500, customer deadlines 9 500, spontaneous conflicts 12 500, API changes with 3 services 16 500 and with 4 services 21 500. The top bar shows the next one under the score (`nextUnlock`, `UNLOCK_ICON`, `#goal`). Passing a threshold brings that kind right away (`introduceNext`, forcing the spawn via `G.forceSkip`/`G.forceGroup`/`opts.due`). Spawning checks `ready(key)`, not just `unlocked(key)`: a kind's first appearance waits until the kinds before it in `UNLOCK` have been seen, so info cards always come in that order. There's no minimum time between info cards (the user removed the 20-second rule once progression was star-based), so passing several thresholds in one release brings their cards one after another. Git conflicts can happen from the start.
- **The pace follows the clock, not the score.** `fallTime()` and `spawnInterval()`: sprint 1 (`WARMUP`) eases from calm onto the normal curve, which then tightens slowly over 7–10 minutes. The pace counts cards, not spawns: `spawnRandom` returns how many cards it brought (an API change one per service, a skipped migration two, counted through `G.scheduled`), and the next spawn waits that many intervals. After PI planning, the cards that landed during it (`G.pi.added`) also count, capped at `PI_BREATHER` s, so new cards don't pile in on top of them. The curve runs on `paceT()`, which holds still through sprint 7 (the user found sprint 7 too hard and 5–6 just right), so everything after sprint 6 comes one sprint later. Bots in the tests' balance report vary a lot from game to game (roughly 2–9 minutes); an idle player lasts about 2 minutes.

**PI planning** comes after every third sprint (`PI_EVERY`): when the sprint ticks over to 4, 7, 10 …, `startPI` sets `G.pi` and `frame` calls `piUpdate` instead of `update`, so nothing spawns, falls or counts down, and `G.t` stands still (lead time starts when the sprint does). Deploys keep running to the end, and a queued release follows, so planning starts with empty lanes. First a little platform level drawn on `#pi-canvas` over the radar (`buildLevel`, `piPhysics`, `piDraw`): the avatar (an original, deliberately gender-neutral figure in a hoodie, `drawAvatar`) runs by itself and speeds up toward the finish (`PI_SPEED0` → `PI_SPEED1`, Chrome-dino style; `buildLevel` sizes gaps and desks by the speed at that point, and never puts two gaps back to back), a tap anywhere jumps (`piPress`; double jump, hold for higher), and `PI_CANDIES` candies sit on desks, sticky notes and over gaps. Falling into a gap ends the level (`p.fell`), keeping the candies collected so far. At the finish flag `endHunt` turns each candy collected into a `story` card (✨, 200 p, only from PI), laid out in free space by `placeFree` (or, if the radar is full, left above the edge like any waiting card). `endHunt` also runs everything in `G.scheduled` at once (held-back migrations, missing API clients), so the plan can include them. The player plans calmly: Släpp is disabled (`shipEarly` and `canQueue` refuse during PI; disabled buttons still get `pointerdown`, so the check must be in code), conflicts can be resolved, and `movers` skips the same-service rule, so cards can be replanned one by one. The `#pi-go` button (`data-pigo`), which takes the sprint name's place in the top bar (the schema version stays visible below it) so nothing covers the radar, calls `endPI`.

Info-card texts use plain bullet dots. Keep emojis to the ones that mean something in the game (the icon of the mechanic in the heading, and symbols the player will see, such as ⛔): the user doesn't want decorative ones.

During the level the music switches to an original chiptune loop (`playChipStep`: `chip()` pulse-wave lead and arpeggio, triangle bass, noise drums), and jumps, candies and falls use 8-bit effects (`sfx.chip…`).

**Sound** is all synthesized with Web Audio, with no audio files. The palette is soft and lo-fi: `mallet`, FM `bell`, `wood` (woodblock), `pad` (detuned saws through a lowpass) and `thud`, all built on `tone`/`noise`. The effects live in `sfx`. The music (lo-fi chords Am7–Fmaj7–Cmaj7–G6, soft drums and a random pentatonic mallet melody) is a 16-step sequencer (`musicTick` → `playStep`), called every frame. It schedules about 150 ms ahead, plays faster and opens its filter each sprint, and adds tension voices when `G.danger` (a card near the bottom) is set or a deadline is under 8 s (`G.urgent`). The 🔊 button cycles `soundMode` through `all` → `sfx` (no music) → `off`. Browsers only allow audio after a user gesture, so `initAudio()` runs from the start button.
